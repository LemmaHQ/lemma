# Lemma pre-push checks

Run the relevant local evidence once before a push. Lemma has no Git hooks; CI runs the full workflows on every push to `main`, path-filtered per workflow ([development.md](../../../docs/development.md)). Local checks catch what CI would reject before it costs a round trip.

## Inspect the outgoing change

```sh
git status --short --branch
git log --oneline origin/main..HEAD
git diff --stat origin/main...HEAD
```

The changed directories in that diff decide the checks; uncommitted work is not part of the push and does not count.

## Select checks by changed directory

Run the rows the diff reaches, in this order, once each. Every behavior change also needs its narrowest owning test, which may be a focused run instead of the full recipe.

| Changed | Run |
| --- | --- |
| `crates/`, `Cargo.toml`, `Cargo.lock` | `just rust-fmt-check`, `just rust-lint-check`, `just rust-test` (or `cargo nextest run -p <crate>` when one crate changed and no dependent's behavior can change) |
| `proto/` | `just proto-lint-check`, `just proto-fmt-check`, `just proto-build`, `just proto-gen`, then the `web/` and `crates/` rows, since both consume the contract |
| `design/` | `just design-gen` (its reference and parity checks), then the `web/` row; the `desktop/` and `mobile/` rows when a semantic color name changed |
| `web/` | `just web-fmt-check`, `just web-lint-check`, `just web-build`, `just web-test`; also `just desktop-build`, since Desktop CI builds the renderer from `web/` |
| `desktop/` | `just desktop-fmt-check`, `just desktop-lint-check`, `just desktop-build`, `just desktop-test` |
| `mobile/` | `just mobile-fmt-check`, `just mobile-android-lint-check`, `just mobile-android-build`, `just mobile-android-test` |
| Any `*.md`, `*.i18n.yaml`, `scripts/`, `docs/i18n/terminology.md` | `just docs-pairing-check`, `just docs-lint-check` |
| `justfile`, `mise.toml` | every changed recipe once; every workflow's path filter includes both files |
| `.github/workflows/` | read the changed workflow for path filters and job dependencies; it runs only in CI |

Notes on the rows:

- Rows that compile the Rust workspace or the Android app (`crates/`, `proto/` through its `crates/` row, `mobile/`) need the user's consent first. Without it, report those rows as not run; never as passing.
- Compiling the Rust workspace compiles `lemma-server`, which embeds `web/dist`; run `just web-build` first when `web/dist` is missing or stale.
- Generated code is gitignored and regenerated by CI; run `just proto-gen` or `just design-gen` locally before a build that reads it.
- Real-provider behavior: when a change can alter what a model sees or does, also run the relevant `#[ignore]` tests with credentials (`cargo test -p <crate> -- --ignored`). Never print keys.
- When the change adds or alters an async, resource-owning, or global-state test, apply [lemma-ci-test-reliability](../lemma-ci-test-reliability/SKILL.md) first.

Do not repeat a check that already passed on the same content merely because a commit or push follows.

## Full local run

Running every row above is the full local run; no single recipe aggregates them. Run it only when the user asks, while diagnosing a CI failure, or when the change spans the repository so broadly that no narrower set is credible. It compiles the Rust workspace and the Android app, so it needs the same consent.

## Handle failures

If a selected check fails, stop and fix it or report the blocker; do not push and hope CI differs. If a failure looks environment-specific (Windows paths, line endings, a missing NDK or PostgreSQL), record the exact command and mismatch, confirm the rest of the evidence, and tell the user before pushing.

## Push

Push only on the user's explicit request.

1. Run the selected checks once.
2. Push normally; never `--force` to `main`. Rewriting pushed history needs the user's explicit instruction and `--force-with-lease=main:<observed-oid>`.
3. Verify the remote matches local `HEAD`: `git rev-parse HEAD origin/main`.
4. Inspect CI: `gh run list --branch main --limit 5`, then `gh run view <id>` for any failure. Report pending runs as pending, and inspect a failure before attributing it to the change or the environment.
